# Introspected application database

`schema.prisma` was generated by Prisma 7.10.1 from the database configured in
`web/.env` on 29 October 2026. It is a standalone snapshot of the actual deployed
tables, separate from the application schema in `web/prisma/`. It was refreshed
after all seven application migrations were deployed to this database.

Verified connection:

- Database: `newmeta_app`
- Direct endpoint: `ep-odd-surf-aoil4uxa.c-2.ap-southeast-1.aws.neon.tech`
- PostgreSQL: 18.6
- Connection default: `transaction_read_only = on`
- Non-system schemas: `public`, `mirror`
- Tables: 42, including Prisma's internal migration ledger
- Introspected application/session models: 41
- Applied application migrations: 7, with matching local checksums

The database now includes ingestion runs, generations, publications, the catalog,
typed metafields, frozen selections, operation state and the catalog-import queue.
The original Shopify session tables in `public` are unchanged. The application
still uses its existing pooled connection; the ignored local environment now also
contains the matching direct connection for Prisma migrations, with the migration
ledger in `mirror`.

Both the canonical application models and this introspected snapshot have zero
Prisma schema drift against live. All 28 physical filter bindings verify, and 29
custom database triggers are installed. This establishes schema readiness; a
merchant must still authenticate and run an initial catalog sync to publish data.

To refresh from `web/`, use Prisma 7.10.1:

```powershell
npx --package prisma@7.10.1 prisma db pull --config prisma-live.config.mjs
node scripts/normalize-live-schema.js
npx --package prisma@7.10.1 prisma validate --config prisma-live.config.mjs
```

The config reads the existing environment, prefers an explicitly configured
direct connection and otherwise derives the matching direct Neon endpoint. It
sets read-only mode and bounded statement/lock timeouts. Credentials are never
embedded in the generated schema or this document. Existing application schema
files are not an introspection target. The normalization step fixes Prisma
7.10.1's inferred publication reverse relation to the same collection used by
the canonical models, without adding a fictitious unique key. A subsequent
database-to-snapshot diff confirms this changes no physical schema contract.

Prisma's check-constraint introspection warnings do not remove database guards.
The migration SQL remains authoritative for checks and triggers that Prisma
cannot fully represent.
